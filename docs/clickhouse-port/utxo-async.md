## 1. Decisions 1–3

- **`p_node_tx` default on.** `optionalDdlItems.p_node_tx.default = true` (`ddl-apply.ts`). `applyClickHouseDdl`,
  the DDL CLI and `apply.sh` apply the default items, plus any named in `CHAINGRAPH_CLICKHOUSE_DDL_OPTIONAL`, minus
  any named in `CHAINGRAPH_CLICKHOUSE_DDL_SKIP` (CLI: `--optional`, `--skip`). The CLI still materializes a projection
  once when it adds it to a filled table. `applyClickHouseDdl(…, { optional: [] })` applies none. The API notices the
  projection as before; without it the same results come from the id range. Unit test of the resolution; the e2e
  acceptance-order spec now gets the projection from the harness without asking.
- **Aggregates.** No code change: the aggregate budget stays 30 s. The node's UTXO count/value and per-category
  totals no longer need it (§3); every other whole-chain aggregate still fails fast.
- **`block_inclusions` order.** Default `ORDER BY height, block_hash` (also the tie-break of any explicit order).
  The inclusions are read once (a statement-level CTE) and joined to `block_at` for height and hash; with
  `order_by: { block_internal_id }` and no block field selected the join is skipped (storage order).
  `api-structural.spec.ts` checks the fork case (two blocks at height 2, ordered by hash) and the storage order.
  The catalogue's 63 documents still equal v1 (§6).

## 2. Design

### 2.1 Definition

Chaingraph v1's, per node n at a commit seq X: output o is unspent iff the transaction creating o is accepted by n
at X (a block n accepts or n's mempool: `tx_acceptance` rows of n with seq at most X, `sum(sign) > 0` per
(transaction, block)) and no input of a transaction accepted by n at X spends o. Every acceptance fact is per node;
nothing answers for "any node". Structural facts (outputs, inputs) are node-agnostic and immutable.

### 2.2 Tables (`ddl/090_utxo_set.sql`)

| Object | What | Key / partition |
|---|---|---|
| `utxo_set` | signed rows (+1 entered, −1 left) per node and **generation**, tagged `batch` = the batch end (a commit seq) that wrote them; the output's columns | PRIMARY KEY `(token_category, nonfungible_token_commitment_key)`, rows sorted by outpoint within; projection `p_script` by `locking_bytecode_prefix`; PARTITION BY `(node, generation)`; minmax on `batch` |
| `utxo_total` | the same rows summed per (node, generation, batch, token category): outputs, value, fungible outputs and amount (Int128), non-fungible outputs | filled by `utxo_total_mv` on every insert into `utxo_set`; ORDER BY `(token_category, batch)`, PARTITION BY `(node, generation)` |
| `utxo_watermark` | one row per published batch end, build or rebase: (node, watermark U, generation, kind, rows, epoch) | ORDER BY `(node, watermark, generation)` |
| `utxo_build_spent` | work table of a bulk build (spent outpoints per node and generation); empty outside a build | ORDER BY outpoint, PARTITION BY `(node, generation)` |
| `utxo_set_at` | parameterized view of the read rule for ad-hoc readers (parity, tools); generated by `utxoSetViewStatement`, checked by `utxo-set.spec.ts` | |
| `node_block`, `node_transaction` | `mm_commit_seq` minmax skip index (the change steps start from a node's rows in a seq range) | |

The set of n at a published U of generation g is `GROUP BY outpoint HAVING sum(sign) > 0` over the rows of (n, g)
with `batch <= U`. Plain MergeTree: no merge ever cancels rows, so a reader holding an older U still reads exactly the
set at that U.

### 2.3 Change rows of (from, to] (`utxoChangeSql`)

Five steps, each a WITH **scalar** (an array evaluated once; a `MATERIALIZED` CTE chain was re-analysed per
reference: the first step 12 times, ~200 ms of planning for a one-commit correction, now ~50 ms):

1. **touched**: transactions with an acceptance row of n in (from, to], found through the commits' `node_block`
   rows (→ `block_transaction`) and `node_transaction` rows. Every `tx_acceptance` row is written in the same commit
   as one of those (block save, header acceptance, re-org, mempool add/replace/confirm/expire).
2. **changed**: those whose acceptance by n at `from` differs from that at `to` (one read of their acceptance rows by
   the primary key: `sumIf(sign, seq <= from) > 0` vs `sum(sign) > 0` per (transaction, block)).
3. **affected**: outputs the changed transactions create and outputs they spend.
4. **spenders**: every stored input spending an affected output (`input.p_outpoint`).
5. **involved**: acceptance at `from` and at `to` of the affected outputs' creators and of the spenders.

Per affected output: `in(x) = creator accepted at x AND no spender accepted at x`; one row with
`sign = in(to) − in(from)` where that is not 0. An output outside the affected set keeps its membership: neither its
creator's acceptance nor any spender's changed. Output and input rows are read at the snapshot's node-agnostic gate,
which shows every row of a transaction a seq up to visible(n) accepts; void and fenced seqs are excluded by the
same gate as every reader.

### 2.4 The maintainer (`UtxoSetMaintainer`, `utxo-set.ts`)

A background task of the writer (the lease holder), started with each epoch like the spend index
(`CHAINGRAPH_CLICKHOUSE_UTXO_SET`, default `on`). It never runs on a commit path and never waits for a commit; the
visibility publisher pokes it after each publish. Per pass, per node:

- **No set yet**: if the node has ≥ 1,000 committed commits or ≥ 2 M recorded acceptance rows, a **bulk build** (the
  query-time set at visible(n), published as generation g+1 at U = visible(n)); else replay from 0. The build is
  memory-bounded: phase 1 writes the outpoints spent by the node's accepted transactions into the work table
  `utxo_build_spent`, one slice of spender hashes at a time; phase 2 writes the outputs of the node's accepted
  transactions minus that slice's spent outpoints, one slice of creator hashes at a time. One slice per 8 M acceptance
  rows (16 to 256). A one-statement build needed > 33 GiB at synthetic mainnet scale (37 %); this one 1.4 GiB per
  statement.
- **Batch**: the committed commits of n in (U, visible(n)], as many as fit 200 k recorded acceptance rows (at least
  one); insert the change rows of (U, to] tagged `batch = to`; publish `to`. No commit of n in the range: nothing is
  written or published (readers see `lagCommits = 0`).
- **Rebase** (after a batch): when the generation's rows exceed max(1 M, 2 × its base rows), or its `utxo_total` rows
  exceed 2 M: check the invariant (every outpoint's sum of signs is 0 or 1; a violation is reported as
  `utxo_set_invariant_violation`, logged at fatal level, and no rebase happens), then write the set at U as
  generation g+1 (sign +1, batch U) and publish (U, g+1). The old generation's partitions and marks are dropped
  10 minutes later (a reader never picks an older generation once a newer mark exists at the same U).
- **Restart**: rows of unpublished batches, builds and rebases (`batch > U` of the generation, or a newer generation)
  are deleted first (`removeUnfinished`). Dedup tokens carry a per-run id.
- **Progress**: `utxo_set_progress` (info, at most every 10 s): node, watermark, visible, generation, lag in commits,
  rows, batch time. `ClickHouseStore.utxoSetStatus()`, `catchUpUtxoSet()`, and the test hook `holdUtxoSet(seq)`
  (a paused or lagging job).

### 2.5 Read rule

Every request takes ONE snapshot; with the stored set it also carries, per pinned node, the mark
`(U, generation, lagCommits, lagRows)`: the newest published `(U, generation)` with `U ≤ visible(n)`, and the
node's committed commits (and their recorded acceptance rows) in (U, visible(n)]. Readers take:

- the stored rows of (n, g) with `batch ≤ U`, filtered by the request's output predicate, **plus**
- the change rows of (U, visible(n)], same predicate (left out when `lagCommits = 0`),

collapsed per outpoint (`HAVING sum(sign) > 0`). Every row of an outpoint carries the same output columns, so
filtering before the collapse is exact. The stored part is the set at U (§2.2); the change part is exactly
`in(visible(n)) − in(U)` (§2.3); their sum is the set at visible(n). **Exact at the snapshot whatever the lag.**

Totals follow the same rule: `utxo_total` rows of (n, g) with `batch ≤ U`, plus the change rows of (U, visible(n)]
summed per category.

`SnapshotCache` reuses a snapshot only while visible(0), every visible(n) **and** every node's newest mark are
unchanged (a cached lower U would be exact but would pay the correction until the next commit). The response cache
keys on the visibility watermarks only: a hit is an answer computed at one earlier snapshot with the same watermarks,
exact regardless of the U it used.

### 2.6 Invariants

1. Every outpoint's sum of signs over (n, g, batch ≤ U) is 0 or 1 for every published U (checked at each rebase and
   by `checkUtxoSet`; tests assert it at every published mark).
2. A published (U, g) never changes; rows with `batch ≤ U` of g are never deleted while g is the newest generation
   (only unpublished rows are deleted, and old generations after their grace period).
3. Every seq at or below visible(n) is terminal; voided seqs are void before they are terminal, so the gate a batch
   used for (U, to] equals the gate any later reader uses for the same range.
4. Per node only: the steps read node n's acceptance rows and node-agnostic structure; a fact of another node never
   enters.

## 3. API (`src/api`)

- `ApiDb.utxoSetPolicy` from `CHAINGRAPH_API_UTXO_SET` (`on` | `off`, default `on`) and
  `CHAINGRAPH_API_UTXO_SET_MAX_LAG_ROWS` (default 100,000). Snapshots read the marks when the policy is on and the
  database has `utxo_watermark` (`storeFeatures().utxoSet`).
- `unspentOutputRows`: when `sql.storedUtxoSet(node)` (the statement's primary node has a mark, the policy is on and
  `lagRows ≤ maxLagRows`), the row source is the read rule (`storedUnspentRows`); otherwise the query-time forms as
  before. Used by `unspent_outputs`, `unspent_outputs_aggregate`, `output_groups(unspent: true)` and
  `unspent_output_groups` (holder balances).
- `unspent_outputs_aggregate` without a filter, or with only `token_category: { _eq }`, asking `count` and `sum` of
  `value_satoshis` / `fungible_token_amount`: read from the totals (`runUnspentTotals`); same null rules as the
  general path. Anything else aggregates the row set.
- The plan bound changes plans, never results (G2 spec: above the bound the same 46 output filters × 2 nodes answer
  through query time).

**No data discrepancy in the store was found.** One apparent discrepancy was investigated and explained: in the
agent e2e suite, `checker.forgetNodeValidation` (test fault injection) cancels committed mempool acceptance rows of
node1/node2 at their own commit seq; the −1 and +1 collapse on merge, so the history below the set's watermark
changes without a commit. The stored set (computed before) then keeps those two outputs while the rewritten history
no longer has them (reproduced on the kept database: the creator has no acceptance row left, yet commit 571, a
committed mempool commit of node1, wrote one). No production path writes acceptance rows outside a commit (writers:
`block-commit.ts`, `mempool-commit.ts`, `clickhouse-store.ts` header acceptance and re-org). Any future repair tool that
rewrites acceptance below a published watermark must rebuild the node's set (drop its marks; the maintainer rebuilds).

Two digests used during the work were too weak (`cityHash64` over a NULL argument is
NULL, so rows with a NULL column dropped out of the hash): `checkUtxoSet` and the scripts now hash
`toString(tuple(…))`, and every equality above was re-run or was a row-for-row comparison.

## 7. Known limits

- **Correction cost at mainnet scale.** Behind a block, a filtered unspent statement pays ~0.1 s warm (330
  transactions at 37 % scale; unfiltered totals ~0.2 s) and more cold; mainnet blocks are larger. The job's batch time sets how long that lasts after each
  block (seconds when cold). Mempool commits cost ~40–70 ms per statement. The cost is dominated by spender and
  acceptance lookups (random granules of `input.p_outpoint` and `tx_acceptance`), not by planning.
- **Unfiltered unspent pages** at mainnet scale exceed the data budget (whole-set GROUP BY). Count and value come from
  the totals; pages need a filter (category, script, value range).
- **Lease edge** (as the spend index): an insert of a stale writer that was already sent when its lease was lost
  could land after the new writer resumed from the same mark. The invariant check at every rebase and `checkUtxoSet`
  would report it (`utxo_set_invariant_violation`, fatal log level).
- **Build on mainnet** (golden has no stored set): ≈ 836 s × 2.7 ≈ 40 min at one slice per 8 M acceptance rows
  (≈ 53 slices), bounded memory; to be measured.
- **Rebase on mainnet**: a full rewrite of ≈ 125 M rows when the change rows reach the base size or the totals reach
  2 M rows (at tip rates: weeks); old generation kept 10 min.

## 11. Spot-check (owner decision 2026-10-12; fix pass 4)

The maintainer compares its stored set with the query-time answer every `CHAINGRAPH_CLICKHOUSE_UTXO_SET_SPOT_CHECK_MS`
(default 3,600,000, hourly; 0 = off), in the background (never two rounds at once; `stop()` waits for a running one).
Per node with a published mark, at ONE snapshot (`spotCheckUtxoSet`, `utxo-set.ts`):

| scope | chosen | compared |
|---|---|---|
| 3 token categories | random among the node's `utxo_total` categories (small table, key read), never the zero category | rows (count + XOR of per-row digests, as `checkUtxoSet`) and the category's totals |
| 3 locking-bytecode prefixes | from the 64 outputs at a random transaction hash (output key) | rows |
| the node's totals | | per-category totals of the whole set (count, value, fungible and NFT counts, digest) |

The stored side is the read rule (stored rows up to U + correction to visible(n)); the query-time side is
`unspentAtQueryTimeSql` with the scope as a filter (inputs read only for the scope's outpoints, `input.p_outpoint`).
Each statement has a 120 s budget; a scope over it is counted as skipped, not as a mismatch. The whole-set totals scope
is the expensive one on mainnet (a whole-chain query-time count: U4 timed out at 30 s on golden through the API); its
cost is to be measured on GKE, and `spotCheck.totals: false` turns it off if it is too heavy.

A mismatch is a data discrepancy: diagnostic `utxo_set_spot_check_mismatch` (node, generation, U, visible(n), scope,
value, both answers), logged at **error** level by the agent; each round logs `utxo_set_spot_check` at info. Counters
in `utxoSetStatus()` (`spotChecks`, `spotCheckScopes`, `spotCheckMismatches`, `spotCheckSkipped`) and on the agent's
internal API at `/metrics` (Prometheus text: `chaingraph_utxo_set_spot_check_mismatches_total` etc.).

Tests (`utxo-set.spec.ts`): random scopes equal on both nodes; `ClickHouseChecker.forgetNodeValidation` (the
history-rewrite helper) on node 1's token transaction makes the category, prefix and totals scopes differ on node 1
only, reported with both answers and counted (metric text checked); the loop runs on its own every
`spotCheckIntervalMs`. Chipnet: the spot-check of `ch1_fix4_chip` (fix-pass-4.md) is equal.
